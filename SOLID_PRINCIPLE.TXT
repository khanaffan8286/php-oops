SOLID is not a design pattern.

It is 5 principle for writting the code.

1. SRP -> SINGLE RESPONSIBLILTY PRINCIPLE

A CLASS HAVING ONE REASON TO CHANGE
ONE CLASS SHOULD HAVE ONE RESPOSIBILITY 

ONE CLASS = ONE JOB 

EXAMPLE:
         WRONG : ORDERCONTOLLER : VALIDATE + SAVE + EMAIL + PAYMENT
         RIGHT : ORDERSERVICE : ONLY HANDLE THE LOGIC 

WHY : EASY TO HANLDE CHANGE DEBUG

CORRECT WAY : ORDERCONTOLLER -> StoreOrderRequest,ORDERREPORTING,EMAILSERVICE,PAYMENTSERVICE.

2. OPEN/CLOSED PRINCIPLE

OPEN/CLOSED PRINCIPLE MEANS A SOFTWARE SHOULD IS OPEN FOR EXTENSION AND CLOSED FOR MODIFICATION
WE SHOULD ADD A NEW CODE WITHOUT CHANGING THE OLD CODE 

WHY IMPORTENT
NO RISK OF BREAKING THE OLD CODE 
IMPROVE MAINTIBILTY 
SCALABLE ARCHITECURE
EASY TO ADD NEW FEATURE

BAD EXAPMLE 

class PaymentMethod
    {
      public function pay(){
              if ( $method == paypal){
                // paypal logic}
              elseif ($method == stripe){
                // stripe logic }
               }
    }


CORRECT EXAPMLE 

interface PaymentInterface
{
    public function pay();
}

class PaypalPayment implements PaymentInterface
{
    public function pay()
    {
        // paypal payment
    }
}

class StripePayment implements PaymentInterface
{
    public function pay()
    {
        // stripe payment
    }
}

class PaymentService
{
    public function process(PaymentInterface $payment)
    {
        $payment->pay();
    }
}


3 . LISKOV SUBSTITUTION PRINCIPLE -> OBJECT OF A CHILD CLASS SHOULD BE REPLACABLE WITH THE OBJECT OF THE PARENT CLASS WITHOUT BREAKING THE CODE.


Meaning:

child class must properly follow parent behavior
no unexpected behavior
inheritance should not break logic

Bad Example (LSP Violation)

class Bird
{
    public function fly()
    {
        return "Flying";
    }
}

class Ostrich extends Bird
{
    public function fly()
    {
        throw new Exception("Ostrich cannot fly");
    }
}

Correct Example

interface Bird
{
    public function move();
}
class Sparrow implements Bird
{
    public function move()
    {
        return "Flying";
    }
}
class Ostrich implements Bird
{
    public function move()
    {
        return "Running";
    }
}

4. INTERFACE SEGREGATION PRINCIPLE -> CLIENT DO NOT USE UNWANTED METHOD THAT THEY NOT USE.

BAD EXAMPLE

interface PaymentInterface
{
    public function pay();
    public function refund();
    public function cancel();
    public function verify();
}


Correct Example

Split interfaces.

interface PayInterface
{
    public function pay();
}
interface RefundInterface
{
    public function refund();
}
interface VerifyInterface
{
    public function verify();
}

Now classes only implement what they need.

class StripePayment implements PayInterface, RefundInterface, VerifyInterface
{
    //
}



5. D — Dependency Inversion Principle (DIP)

Depend on interfaces/abstractions, not concrete classes.
